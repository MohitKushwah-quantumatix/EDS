## Points resolved without escalation

1. **The suggested rate and the expected volume are inconsistent.** 18 per cent
   of the 381 eligible items averages 68.6 reviews, below the stated 70-90
   range; that range implies roughly 444 eligible items. The shipped rate was
   left at the documented 18 per cent rather than raised to the ~21 per cent
   that would centre the range, because the rate is the figure the
   specification actually names and it is configuration driven. The arithmetic
   is reported in [03_Review.md](03_Review.md).
2. **`customers.parquet` is listed under F001 but is generated by F002.** The
   file exists either way, so the dependency is satisfied and no action was
   needed beyond noting it.
3. **F010 produces a single dataset with no orchestrator-level history.** Every
   earlier commerce feature produced a parent plus a collection and a status
   history; a review has neither, so `REVIEW_DATASETS` is a one-element tuple.
   `reviews.py` still exists, because the CLI and the tests reach every feature
   through the same shape.
4. **A returned item is excluded even though it was delivered.** The rule is
   the conjunction the specification states, and both halves are asserted
   separately so neither can silently stop being applied.
5. **The rating draw uses `Expr.cut` rather than a comparison chain**, so the
   number of ratings stays configuration driven without a Python loop over
   rows. This replaces the per-row helper F009 used for refund types.
